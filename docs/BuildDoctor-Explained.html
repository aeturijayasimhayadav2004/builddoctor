Section 01

The thirty-second pitch

Say this

"BuildDoctor is a GitHub App that watches repositories for failing CI runs. When a build fails, it downloads the log, cuts it down to the lines around the error, sends that to an LLM along with the code diff that triggered the run, and posts a comment on the commit explaining what broke. It also classifies each failure into one of three lanes — and if the failure looks transient, it re-runs the job by itself."

"It remembers. Every diagnosis is stored with a vector embedding of the log, so when a similar failure happens again it passes the previous diagnosis to the model as a hint."

The three lanes

LaneMeaningAction taken
informationalA real code or config error a human must fixPost an explanation, stop
safe_auto_fixTransient — network blip, flaky test, runner hiccupRe-run the failed job automatically
needs_reviewAmbiguous, or touches something sensitiveFlag it for a person
The honest boundary — say this before you are asked

It never writes code. It does not push commits, open pull requests, or edit files, and the App's permissions do not allow it to — contents is read. The only write actions are: post a comment, add a label, re-run a job. That limit is deliberate; an agent that edits your code on a guess is a liability, not a feature.

Why this is a real project and not a toy

  • It has real users. Three live installations, one belonging to somebody who is not the author.
  • It is measured. A 24-case golden set scores the classifier at 91.7% overall, 95.2% on unambiguous cases. Regressions are caught by re-running it.
  • It fails closed. Every access decision defaults to "no" when evidence is missing.
  • It survived its own security incident. A secret leaked in Phase 10; the response is written up in the README rather than hidden.

Section 02

The lifecycle of one failing build

This is the answer to "walk me through what happens." Ten steps.

1
GitHub sends a webhookA workflow_run event with action completed hits POST /webhook. GitHub expects a reply within 10 seconds.
2
Verify the signatureHMAC-SHA256 over the raw body using WEBHOOK_SECRET, compared with hmac.compare_digest. Fails → 401, nothing else runs. This happens first, before parsing.
3
Check the gateLook up installations.is_allowed for this installation id. Closed → log and drop. No log downloaded, no model called, no money spent.
4
Reply 200 immediately, work in the backgroundThe real work is handed to a background task so GitHub's 10-second clock is never at risk. A slow LLM must not mark the App as a broken integration.
5
Mint a scoped tokenapp_auth.py signs a JWT with the App's private key, trades it for an installation access token scoped to that one installation, expiring in 1 hour. Cached in memory until then.
6
Gather evidenceList the failed jobs → download their logs → cut each to 5 lines before / 10 after each ##[error] marker → fetch the diff (PR diff, or commit vs parent).
7
Search memoryEmbed the excerpt into 384 dimensions, then a pgvector cosine search over past diagnoses. A match above 0.90 similarity becomes a hint for the model.
8
ClassifyThe LangGraph classify node calls the LLM with the excerpt, the diff, and any past match — asking for a diagnosis and a lane, as structured JSON.
9
Route and actThe graph routes on the lane to an action node, which calls the MCP server over HTTP: post a comment, add a label, or re-run the job.
10
RecordWrite a row to diagnoses — repo, run id, lane, excerpt, diff summary, diagnosis text, installation id, and the embedding, so this failure is findable next time.
Measured, not estimated

End to end, on a warm server: ~18 seconds from the build failing to the comment appearing. Measured today — see section 9.

Section 03

Architecture

Four logical components

ComponentJobWhere it runs
Web appWebhooks, OAuth sign-in, the read API, the admin routesFastAPI, one Render web service
Agent graphClassify → route → act, as a state machineLangGraph, in-process
MCP serverThe four tools that actually write to GitHubMounted at /internal/mcp in the same process
DashboardEvery diagnosis, and the approve/revoke panelReact SPA, served at /dashboard/
The question this design invites

"Why is the MCP server a separate service at all if it runs in the same process?"

Because the boundary is the point, not the process count. Every action that writes to GitHub is reachable exactly one way — through a described, typed tool call. The agent cannot reach github_client.py directly. That means the complete list of things this agent can do to your repository is four function signatures, and you can read all four in a minute.

Under Docker they genuinely are separate containers. On Render they were merged into one process by server_combined.py — because the free tier gives one service, and paying for architectural purity when the boundary is enforced in code anyway is a bad trade.

The four MCP tools — the complete write surface

ToolDoes
post_pr_commentComment on a pull request
post_commit_commentComment on a commit
add_pr_labelAdd a label to a PR
rerun_workflow_jobRe-run a failed job
The re-run loop guard

An agent that re-runs failed jobs can loop forever: re-run fails → webhook → re-run. The guard uses GitHub's own run_attempt field — BuildDoctor only ever re-runs attempt 1. Attempt 2 failing is classified but never re-run.

Crucially this is stateless: the counter is GitHub's, not a variable in memory that a restart would reset. That is the difference between a guard and a hope.

The MCP endpoint is public but unusable

The MCP server is mounted inside a public web service, so its URL is reachable. It refuses anyway: mcp_server.py checks the Host header against an allowlist and answers 421 Misdirected Request on a mismatch. A request through Render's router carries Host: builddoctor.onrender.com, which is not on the list. The app's own call carries Host: localhost:10000, which is.

Verified both directions before deploying: 421 for a foreign Host, successful handshake listing all four tools over loopback.

Section 05

External services — what, why, and what was rejected

Six things this project does not own. For each, an interviewer's real question is "why that one?"

GitHub — the platform required

Source of webhooks, logs, diffs; destination for comments. Integrated as a GitHub App, not a personal access token.

Why an App: a PAT carries one human's full access to everything they can see, never expires until revoked, and cannot be scoped per repository. An App gets an installation token scoped to one installation, expiring in an hour by itself. When Phase 10 leaked a secret, that difference is what limited the blast radius.

Groq — LLM inference required

Runs openai/gpt-oss-20b. Called through the OpenAI SDK, because Groq is API-compatible.

Why Groq: speed and a free tier. Inference sits inside GitHub's 10-second webhook window (mitigated by backgrounding, but latency still matters). Why an open-weights 20B rather than a frontier model: the task is bounded — read an error, name the cause, pick one of three labels. The eval says 95.2% on clear cases. Paying frontier prices for that would be waste.

The trade admitted: the SDK is OpenAI's, so switching providers is a base-URL change. That is deliberate portability, not lock-in.

Neon — Postgres with pgvector required

Stores every diagnosis and the installations table.

Why not Render's own Postgres: Render's free database expires 30 days after creation. For most projects that is an annoyance. Here it is fatal — the whole point of the embedding search is recalling failures from weeks ago. A database that deletes itself every month is not memory. Neon's free tier does not expire.

Why pgvector rather than a vector database: at this scale the vectors belong next to the rows they describe. A separate Pinecone or Weaviate would add a service, a sync problem, and a second failure mode to solve a problem that ORDER BY embedding <=> query already solves.

Render — hosting required

One free web service running app + MCP server, auto-deploying on push to master.

The cost of free: the instance sleeps after ~15 minutes idle and takes 1–2 minutes to wake. Webhooks that arrive while it sleeps are lost outright — GitHub does not retry. That was measured, not assumed.

cron-job.org — keep-warm mitigation

Pings /health on a schedule so the instance never sleeps and no webhook is lost.

Why not GitHub Actions' own scheduler: it was tried first and it does not work. Measured over 7 hours: a */10 cron should have fired ~42 times and fired 0. GitHub deprioritises scheduled workflows under load with no error and no notification. An external pinger fires on time. This is in the README as a settled finding.

Discord / Slack webhook — owner notification optional, currently off

One line of text when a private-repo installation needs manual approval.

Currently unset by choice. The message goes to the server log instead. The consequence is stated honestly in the install guide: an installer must message the owner, because nothing else will.

Section 06

The data model

Two tables. Deliberately small.

diagnoses — what happened

ColumnHolds
idPrimary key
run_idGitHub's workflow run id — links back to the actual run
repoowner/name
created_atTimestamp
log_excerptThe trimmed log — what the model actually saw
diff_summaryThe change that triggered the run
diagnosis_textThe model's explanation
posted_toWhere the comment landed
laneThe classification
embeddingvector(384) — this is what memory searches
rawThe full model response, kept for debugging
installation_idWhich installation produced it — the multi-tenant key

installations — who is allowed

ColumnHolds
installation_idGitHub's id for the installation
account_loginUser or org name
account_typeUser or Organization
is_allowedThe gate. Read on every single webhook
approval_sourceauto_public · owner · NULL
Why approval_source had to exist

Public-only installations approve themselves. But an install that was all-public can later add a private repo — and then automatic approval is a promise that is no longer true, so it must be withdrawn.

The problem: is_allowed = true looks identical whether the App set it or a human did. Withdrawing blindly would let the App overrule a decision the owner made on purpose. So the reason is recorded. Only auto_public is ever auto-withdrawn; owner and NULL never are.

Rows predating the column are NULL, not backfilled to owner — because backfilling would write a guess into a column that governs access.

Withdrawal is one-way — and that is the interesting bit

Making a repo private withdraws approval. Making it public again does not restore it.

Why: if it did, approval would be reversible by anyone who can toggle a repository's visibility. The gate would be controlled by the applicant rather than the approver. Proven live: privatized closed the gate; publicized arrived three minutes later and did nothing.

Schema changes without Alembic

Migrations are a list of (description, SQL) pairs in db.py, run at startup, all written IF NOT EXISTS so re-running is safe. Why not Alembic: at two tables and a handful of additive changes, Alembic is a dependency, a directory, and a mental model to solve a problem this project does not have yet. The trigger to adopt it is the first destructive migration — a column rename or drop — not the calendar.

Section 07

The decisions worth defending

This is the section that matters. Each is a decision, a reason, and a rejected alternative.

1 · The 0.90 similarity threshold was derived, not guessed

Memory only helps if "similar" means similar. The threshold was set by measuring real embedding distances between known-related and known-unrelated failure pairs, then picking the value that separated them. Below it, unrelated failures started matching and the hint made diagnoses worse.

The honest bit: the eval later found a defect in the untested middle zone around the boundary — and that finding, plus the fix, is written up in the README. A number you can defend with a measurement beats a number that happens to work.

2 · Failing closed, everywhere

  • A repository object with no private key reads as private (.get("private", True)) — so a payload shape change makes installs wait for a human, not sail through.
  • An empty repository list is no evidence, and no evidence cannot support a yes.
  • An "All repositories" install is refused even when everything is public today, because it silently covers repos created tomorrow.
  • A model response that will not parse falls back to informational — the lane that only ever posts a comment.

3 · The field is private, not visibility — and I checked

GitHub's webhook reference documents that an installation payload contains a repositories array, but not what is inside each object. Assuming visibility — the field the REST API returns — would have shipped a bug that silently made every install look private.

Instead: GET /app/hook/deliveries, read a real delivery, and confirm the objects carry exactly five keys — id, node_id, name, full_name, private. Ask the system that owns the fact. That habit is the single most transferable thing in this project.

4 · Permission changes are asymmetric

Before narrowing contents from write to read, the docs were checked rather than assumed. GitHub: adding permissions requires every installation to re-accept by hand; removing them takes effect immediately. Verified afterwards in practice — both installations moved to contents: read with the same updated_at, no suspension, no action required from anybody.

5 · The user's GitHub token is thrown away

At the end of OAuth, the access token and its 6-month refresh token are discarded. Only the GitHub user id and login go into a signed session cookie.

The cost, stated: the installation list is a snapshot from login, so a newly installed App is invisible until re-login — hence the "Refresh access" button. The alternative rejected: storing a live GitHub credential in a signed-but-not-encrypted cookie, or in the same Postgres the dashboard reads. A button press twice a day beats a stored credential.

6 · A secret leaked, and the response is documented

Phase 10 found a leaked secret. It was rotated, the exposure verified closed, and the whole incident written into the README rather than quietly fixed. An interviewer will respect this far more than a project claiming it never happened. The reason the blast radius was small is decision 1 in section 5 — scoped, self-expiring installation tokens rather than a personal access token.

7 · Knowing what you have not built

The README carries a "Deliberately not done" section: no pagination, no second approver, no refresh-token policy, no scheduled visibility re-check. Each says what would trigger building it — "the trigger is the row count, not the calendar."

Being able to name your own gaps, with the condition that would change your mind, reads as engineering judgement rather than an unfinished project.

Section 08

Interview questions, with answers

Thirty questions. The amber line says what the question is really testing.

Opening — they are checking you can explain your own work

01Tell me about this project.

Use the pitch in section 1 verbatim. Thirty seconds, then stop and let them steer.

Testing Whether you can compress. Rambling here costs you the interview.
02Walk me through what happens when a build fails.

The ten steps in section 2. Emphasise the order: signature → gate → respond 200 → background work. The reason 200 comes before the work is GitHub's 10-second timeout.

Testing Do you understand your own control flow, or did you assemble it by trial and error?
03Why an agent? Could this be a script?

Honest answer: most of it could. The agent earns its place at one point — the decision of which action to take. Classification and routing are a state machine because the lane determines the action, and that needs to be inspectable and testable rather than buried in prompt text. If it only ever posted comments, a script would do.

Testing Whether you use "agent" as a buzzword. Conceding the limit is the strong answer.
04What was the hardest part?

The "repository added to an existing installation later" case. Auto-approval is a promise that every covered repo is public — but repos can be added after. Revoking blindly would overrule a human's deliberate approval; not revoking leaks auto-approval into private repos. Resolved by recording why the row was approved (approval_source) and only ever auto-withdrawing the App's own decisions.

Testing Whether you have hit a genuinely hard design problem, or only implementation friction.

Architecture

05Why MCP? Why not just call the GitHub API?

To make the write surface enumerable. Every action that touches GitHub goes through one described tool call, so the complete list of what this agent can do is four signatures. Without that boundary, "what can it do to my repo" is answered by reading the whole codebase.

Testing Whether you chose a technology or followed a trend.
06Why LangGraph over LangChain or a plain loop?

Explicit state and explicit routing. The lane decides the next node through a pure function, so control flow is a graph you can read. A prompt-chaining loop hides routing inside the model's output, which is exactly the part you most need to test.

Testing Framework literacy, and whether you can articulate a trade rather than a preference.
07Your MCP server runs in the same process. Isn't the separation fake?

Good question — the process boundary is fake, the code boundary is not. Under Docker they are separate containers. On Render's single free service they were merged by server_combined.py. The enforcement that matters — the agent reaching GitHub only through described tools — is unchanged either way. Paying for a second service to make a diagram honest would be the wrong trade.

Testing Whether you defend a design under pressure or fold. Concede the real point, hold the substantive one.
08How do you stop it re-running a job forever?

GitHub's own run_attempt. Only attempt 1 is ever re-run. Because the counter is GitHub's rather than in-process state, a restart or a redeploy cannot reset it.

Testing Do you understand why stateless guards beat stateful ones?
09What happens if the LLM returns garbage?

Structured output is requested and validated. An unparseable or invalid response falls back to FALLBACK_CATEGORY = informational — the lane whose only action is posting a comment. The failure mode is a less useful comment, never an unintended write.

Testing Whether you designed for the model being wrong.
10How would this scale to a thousand repositories?

Three things break first, in order: (1) the free Render instance — webhook processing is in-process background tasks, so this needs a real queue (Celery, or Postgres-backed jobs); (2) /api/diagnoses uses a LIMIT, not pagination, and silently truncates; (3) the pgvector search is unindexed — it needs an HNSW index, which is one statement.

Testing Can you find your own bottlenecks? Naming three in order is much better than "add caching".

Security and access — usually the deepest questions

11How do you authenticate to GitHub?

As a GitHub App. Sign a JWT with the App's private key (RS256), trade it for an installation access token scoped to one installation and expiring in one hour. Cached in memory for its lifetime. No personal access token anywhere in the system.

Testing Do you actually understand the auth flow you implemented?
12Why not a personal access token? It's simpler.

A PAT carries one human's full access to everything they can see, never expires until revoked, and cannot be scoped per repository. An installation token is scoped and self-expiring. When a secret leaked in Phase 10, that difference is what bounded the damage.

Testing Security reasoning about blast radius, not just "tokens are bad".
13How do you verify a webhook is really from GitHub?

HMAC-SHA256 over the raw request body using the shared secret, compared with hmac.compare_digest — constant-time, so it does not leak the signature through timing. It runs before parsing, because parsing attacker-controlled JSON before authenticating it is the bug.

Testing Whether you know why constant-time comparison and ordering matter.
14Who can approve an installation?

Only the account that registered the App, read from GitHub's GET /app at request time — not from a config file or an env var that could drift out of sync with reality.

Testing Authoritative-source thinking again.
15You auto-approve public repos. Isn't that a security hole?

No, and the reason is the whole argument: a public repository's build logs are already readable by anyone. BuildDoctor reading one discloses nothing that was not already open, so requiring approval would be permitting something already permitted. Private logs are a genuine decision, so a human still makes it. The rule is narrow — it needs an explicitly selected repo list and every repo public.

Testing Can you reason about what a control actually protects, rather than adding controls reflexively?
16Why refuse "All repositories" if everything is public today?

Because approval is a promise about tomorrow. An "all" install covers every repo the account creates from then on. GitHub's own community thread contradicts itself on whether installation_repositories fires for repos created later under an "all" install — so the promise cannot be kept, and it is refused rather than guessed at.

Testing Whether you act on ambiguous evidence by failing closed.
17Someone makes their repo private after being auto-approved. Then?

The repository / privatized webhook fires and approval is withdrawn — but only if approval_source == auto_public. An owner-approved install is never auto-withdrawn, because that would be the App overruling a deliberate human decision.

Testing Did you think past the happy path?
18They make it public again. Does approval come back?

No — deliberately. If it did, approval would be reversible by anyone who can toggle a repository's visibility, which puts the gate in the applicant's hands rather than the approver's.

Testing Whether you can spot a privilege-escalation path in your own design.
19Where do you store the user's GitHub token?

Nowhere. It is discarded at the end of the OAuth callback along with the refresh token. The session cookie holds the GitHub user id and login, signed with itsdangerous.

Testing Session design, and whether you know what you are trading away.
20Your admin endpoint has no CSRF token. Why is that acceptable?

Fair challenge. The mitigation is that the route requires a valid session and that the caller is the App owner, and it was verified that an unauthenticated POST with a well-formed body returns 401 with the row unchanged. It is not a substitute for CSRF protection on a larger surface — with one write route and one authorised human, it is a stated, bounded gap rather than an oversight.

Testing How you handle a real weakness. Defending it as flawless is the wrong answer; naming the bound is the right one.
21Your MCP server is on a public URL. Exposed?

Reachable, not usable. mcp_server.py checks the Host header against an allowlist and returns 421 on a mismatch. Traffic through Render's router carries the public hostname, which is not listed; the app's own loopback call carries localhost:10000, which is. Tested in both directions.

Testing DNS-rebinding awareness — a genuinely advanced answer.

Data, memory, and evaluation

22Explain the memory feature.

Each log excerpt is embedded to 384 dimensions with all-MiniLM-L6-v2, stored in a pgvector column. On a new failure, a cosine search finds the nearest past diagnosis; above 0.90 similarity it is passed to the model as a hint. It is retrieval-augmented generation over the project's own history.

Testing Whether you can explain embeddings without hand-waving.
23Where did 0.90 come from?

Measurement. Distances were compared between known-related and known-unrelated failure pairs, and the threshold set where they separated. Below it, unrelated failures matched and the hint made diagnoses worse. The eval later found a defect in the untested zone near the boundary, which was fixed — that is written up rather than hidden.

Testing The single best question to be ready for. "It felt right" fails. A measurement passes.
24Why a local embedding model instead of an API?

Cost, latency, and disclosure. It is free per call, has no network hop in the hot path, and the log is not sent to a second third party. The weights are baked into the Docker image so a cold start does not pull 90MB from HuggingFace.

Testing Practical cost and latency reasoning.
25How do you know the classifier is any good?

A 24-case golden set with known-correct lanes, in four groups including a deliberately ambiguous "middle zone". Current: 91.7% overall, 95.2% on unambiguous cases. It calls the real classifier — not a copy — but never routes to the action nodes, so running it posts nothing.

Testing Whether you evaluate at all. Most candidate projects do not, and this answer stands out sharply.
26Why report two accuracy numbers?

Because three of the 24 cases are designed to be arguable. Movement on those is noise; movement on the other 21 is signal. Reporting one blended number would hide the distinction that makes the metric useful.

Testing Metric literacy. A strong differentiator.
27Why Postgres + pgvector rather than a vector database?

The vectors describe rows that already live in Postgres. A dedicated vector store would add a service, a sync problem, and a second failure mode to solve something one ORDER BY already solves. The trigger to revisit is scale — and the first fix would be an HNSW index, not a new service.

Testing Resisting resume-driven architecture.

Operations

28What happens if your server is asleep when a webhook arrives?

It is lost. GitHub does not retry. That was measured, not assumed. The fix is an external pinger keeping the instance warm. GitHub Actions' own scheduler was tried first and does not work — over 7 hours a */10 cron should have fired ~42 times and fired 0, silently.

Testing Do you know your system's real failure modes? Admitting lost webhooks is far stronger than claiming reliability you cannot prove.
29How do you know it is working right now?

python preflight.py — ten checks in about thirty seconds. It asks Render, Neon, Groq and GitHub directly, verifies every installation's gate state, confirms the deployed bundle, checks recent webhook delivery outcomes, and asserts the protected routes still return 401. It exists because free-tier dependencies fail silently and uptime proves nothing about the others.

Testing Operational maturity. Very few candidate projects have this.
30What would you do next?

In order: (1) a real job queue so webhook processing survives a restart; (2) pagination before the row count makes LIMIT dishonest; (3) a scheduled visibility re-check, because withdrawal currently depends on webhooks arriving and a sleeping server loses them; (4) an HNSW index when the search gets slow.

Each has a stated trigger. None is "rewrite it in Rust".

Testing Prioritisation. Triggers rather than a wish list is the difference.
