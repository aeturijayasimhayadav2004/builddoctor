Note on use

Sections 1 to 3 constitute an opening account of the system. Section 7 is the material distinguishing an engineer who built something from one who followed a tutorial: each entry is a decision, its justification, and the alternative rejected. Section 8 is for rehearsal.

Section 4 is not for memorisation. Its shape should be familiar; its detail should be looked up. An examiner tests whether a system can be explained, not whether an inventory can be recited.

Summary

Statement of purpose

BuildDoctor is a GitHub App that observes repositories for failing continuous-integration runs. When a build fails it downloads the job log, reduces it to the region surrounding the error, submits that extract to a language model together with the code change that triggered the run, and publishes a comment on the responsible commit explaining the failure.

It additionally classifies each failure into one of three lanes, and where a failure appears transient it re-runs the job without human intervention.

It remembers. Every diagnosis is stored with a vector embedding of the log, so that a recurrence of a similar failure supplies the earlier diagnosis to the model as context.

Classification lanes

Table 1.1 — Lanes and their consequent actions
LaneMeaningAction
informationalA genuine code or configuration error requiring human correctionPublish an explanation; take no further action
safe_auto_fixTransient: network interruption, flaky test, runner faultRe-run the failed job automatically
needs_reviewAmbiguous, or affecting sensitive materialMark for human attention
Limits of authority, to be stated before being asked

The system does not write code. It does not push commits, open pull requests, or modify files, and the application's permissions do not permit it to do so: contents is granted at read. The only write operations available are publishing a comment, applying a label, and re-running a job.

This limitation is deliberate. An agent that edits source code on the strength of an inference is a liability rather than a feature.

Grounds for regarding this as production work

  • It has external users. Three live installations, one belonging to a party unconnected with the author.
  • It is measured. A 24-case reference set scores the classifier at 91.7 per cent overall and 95.2 per cent on unambiguous cases. Regressions are detected by re-running it.
  • It fails closed. Every access decision defaults to refusal where evidence is absent.
  • It has survived a security incident. A credential was exposed during development; the response is documented in the repository rather than concealed.

Processing a failed build

The following is the response to a request to describe the system's operation.

Receipt and authentication

  1. GitHub transmits a webhook. A workflow_run event with action completed is delivered to POST /webhook. GitHub requires a response within ten seconds.
  2. The signature is verified. HMAC-SHA256 is computed over the raw request body using the shared secret and compared using hmac.compare_digest. Failure returns 401 and nothing further executes. This precedes parsing, since parsing attacker-controlled input before authenticating it is itself the defect.
  3. The access gate is consulted. The value of installations.is_allowed is read for the originating installation. Where the gate is closed the event is logged and discarded: no log is retrieved, no model invoked, and no expenditure incurred.
  4. A response is returned immediately. Substantive work is deferred to a background task so that GitHub's ten-second limit is never at risk. A slow model response must not cause the application to be marked a failing integration.

Evidence gathering

  1. A scoped credential is obtained. A JWT is signed with the application's private key and exchanged for an installation access token limited to that single installation and expiring after one hour. The token is cached in memory for its lifetime.
  2. Evidence is assembled. Failed jobs are enumerated, their logs downloaded, and each reduced to five lines preceding and ten following every ##[error] marker. The triggering change is retrieved, being either the pull-request diff or the commit against its parent.
  3. Memory is consulted. The extract is embedded into 384 dimensions and a cosine search performed across previous diagnoses. A match exceeding 0.90 similarity is supplied to the model as context.

Determination and action

  1. The failure is classified. The classification node invokes the language model with the extract, the diff, and any prior match, requesting a diagnosis and a lane as structured JSON.
  2. The result is routed. The graph routes on the lane to an action node, which calls the tool server over HTTP to publish a comment, apply a label, or re-run the job.
  3. The outcome is recorded. A row is written containing the repository, run identifier, lane, extract, diff summary, diagnosis text, installation identifier, and the embedding that renders this failure discoverable in future.
Measured, not estimated

End to end on a warm instance: approximately eighteen seconds from build failure to published comment. Recorded during preparation of this document; see section 9.

On the separation of the tool server

The obvious objection is that the tool server is not a separate service in production, and therefore that the separation is nominal.

The response is that the boundary is the purpose, not the process count. Every operation writing to GitHub is reachable by exactly one route: a described, typed tool invocation. The agent has no access to the GitHub client module. Consequently the complete set of actions this agent may perform upon a repository is four function signatures, all of which may be read in a minute.

Under Docker the components are genuinely separate containers. In production they were combined into one process, the free tier providing a single service. Purchasing a second service to render a diagram accurate, where the boundary is enforced in code regardless, would be a poor exchange.

The re-run loop guard

An agent capable of re-running failed jobs may loop indefinitely: the re-run fails, a webhook is delivered, a further re-run is issued. The guard employs GitHub's own attempt counter; only the first attempt is ever re-run, and a failing second attempt is classified but not re-run.

The property that matters is that this is stateless. The counter belongs to GitHub, not to a variable in memory that a restart would reset. That distinction is the difference between a guard and an expectation.

Exposure of the tool endpoint

The tool server is mounted within a public web service and its URL is therefore reachable. It refuses regardless: the Host header is compared against an allowlist and a mismatch returns 421 Misdirected Request. A request arriving through the platform router carries the public hostname, which is not listed; the application's own call carries a loopback host, which is.

Both directions were verified prior to deployment: 421 for a foreign host, and a successful handshake enumerating all four tools over loopback.

External dependencies

Six services the project does not own. In each case the material question is not what it is, but why that one.

GitHub, the platform

Source of webhooks, logs and diffs; destination for comments. Integrated as a GitHub App rather than by personal access token.

A personal access token carries one person's entire access to everything visible to them, does not expire until revoked, and cannot be scoped per repository. An App receives an installation token limited to one installation and expiring within the hour unaided. When a credential was exposed during development, that distinction bounded the consequence.

Groq, model inference

Executes an open-weights twenty-billion-parameter model, called through the OpenAI SDK, the provider being API-compatible.

Groq was selected for latency and a free allowance; inference falls within GitHub's ten-second window, and although this is mitigated by deferring the work, latency remains material. An open-weights model was preferred to a frontier model because the task is bounded: read an error, name the cause, select one of three labels. The evaluation records 95.2 per cent upon unambiguous cases. Frontier pricing for that task would be waste.

The exchange is admitted: the SDK is OpenAI's, so a change of provider is a change of base URL. This is deliberate portability rather than dependence.

Neon, Postgres with pgvector

Stores every diagnosis and the installations table.

The hosting platform's own free database expires thirty days after creation. For most projects this is an inconvenience; here it is fatal, the purpose of the embedding search being recall of failures from weeks past. A database that deletes itself monthly is not memory. Neon's free tier does not expire.

pgvector was preferred to a dedicated vector database because at this scale the vectors belong beside the rows they describe. A separate store would introduce a service, a synchronisation problem, and a second failure mode, in order to solve what an ordinary ordered query already solves.

Render, hosting

One free web service running the application and tool server, deploying automatically upon push.

The cost of the free tier is that the instance sleeps after approximately fifteen minutes idle and requires one to two minutes to wake. Webhooks arriving during sleep are lost outright, GitHub not retrying. This was measured rather than assumed.

An external scheduler, availability maintenance

Requests the health endpoint on a schedule so that the instance does not sleep and no webhook is lost.

GitHub Actions' own scheduler was attempted first and does not work. Measured across seven hours, a ten-minute schedule should have fired approximately forty-two times and fired none. Scheduled workflows are deprioritised under load without error or notification. An external requester fires punctually.

A chat webhook, owner notification

One line of text when a private-repository installation requires manual approval. Presently unconfigured by choice; the message is written to the server log instead. The consequence is stated plainly in the installation guide: an installer must contact the owner, nothing else having done so.

The necessity of recording the approval source

Installations covering only public repositories approve themselves. An installation formerly all-public may subsequently acquire a private repository, at which point automatic approval represents a promise no longer true and must be withdrawn.

The difficulty is that an allowed installation appears identical whether set by the application or by a person. Withdrawing indiscriminately would permit the application to overrule a decision the owner made deliberately. The reason is therefore recorded, and only automatic approvals are ever withdrawn automatically.

Rows predating the column are null rather than backfilled to owner-approved, backfilling being the writing of a supposition into a column that governs access.

Withdrawal is unidirectional

Making a repository private withdraws approval. Making it public again does not restore it.

Were restoration automatic, approval would be reversible by any party able to alter a repository's visibility, placing the gate in the hands of the applicant rather than the approver. This was demonstrated in production: the privatisation event closed the gate, and the publication event arriving three minutes later produced no effect.

Schema evolution without a migration framework

Migrations are a list of description and statement pairs executed at startup, each written to be idempotent so that repetition is safe. A migration framework was not adopted because, at two tables and a small number of additive changes, it constitutes a dependency, a directory and a conceptual model addressing a problem the project does not yet have. The occasion for adopting one is the first destructive migration, not the passage of time.

Design decisions

Each entry states a decision, its justification, and the alternative rejected.

The similarity threshold was derived rather than assumed

Memory assists only if similarity is meaningful. The threshold was established by measuring embedding distances between known-related and known-unrelated failure pairs and selecting the value separating them. Below it, unrelated failures matched and the supplied context made diagnoses worse.

The evaluation subsequently identified a defect in the untested region near the boundary. That finding, and its correction, are documented. A figure defensible by measurement is superior to a figure that merely happens to work.

Failing closed throughout

  • A repository object lacking the visibility key is treated as private, so that a change of payload shape causes installations to await a human rather than to proceed.
  • An empty repository list constitutes absence of evidence, and absence of evidence cannot support assent.
  • An installation covering all repositories is refused even where all are presently public, since it silently extends to repositories created subsequently.
  • A model response that cannot be parsed falls back to the lane whose only action is to publish a comment.

The payload field was confirmed rather than assumed

The webhook reference documents that an installation payload contains a repositories array, but not the contents of each object. Assuming the field name returned by the REST API would have shipped a defect silently causing every installation to appear private.

Instead a real delivery was retrieved from GitHub's own delivery log and the objects confirmed to carry exactly five keys. Interrogate the system that owns the fact. This habit is the most transferable element of the project.

Permission changes are asymmetric

Before narrowing the contents permission, the documentation was consulted rather than assumed. Adding permissions requires every installation to accept anew; removing them takes effect immediately. This was subsequently confirmed in practice: both installations moved to read access with identical modification timestamps, without suspension and without action by anybody.

The user's credential is discarded

At the conclusion of the sign-in exchange the access token and its refresh token are discarded. Only the user identifier and login are placed in a signed session cookie.

The cost is stated: the installation list is a snapshot taken at sign-in, so a newly installed application is invisible until sign-in is repeated, which is the purpose of the refresh control. The alternative rejected was retention of a live credential in a signed but unencrypted cookie, or in the same database the dashboard reads.

A credential was exposed, and the response is documented

An exposed secret was discovered during development. It was rotated, the exposure confirmed closed, and the incident recorded in the repository rather than quietly corrected. The reason the consequence was contained is the first decision in section 5: scoped, self-expiring installation tokens rather than a personal access token.

Knowing what has not been built

The repository maintains a record of deferred work: no pagination, no second approver, no refresh-token policy, no scheduled visibility re-check. Each states the condition that would occasion building it. The occasion is the row count, not the calendar.

The capacity to enumerate one's own omissions, together with the condition that would alter the judgement, reads as engineering discipline rather than as an unfinished project.

Q3Why an agent? Could this not be a script?

Q4What was the most difficult part?

The case of a repository added to an existing installation. Automatic approval asserts that every covered repository is public, yet repositories may be added afterwards. Withdrawing indiscriminately would overrule a deliberate human approval; not withdrawing would extend automatic approval into private repositories. Resolved by recording why the row was approved and withdrawing only the application's own decisions.

Architecture

Q5Why a tool protocol rather than calling the API directly?

To render the write surface enumerable. Every operation touching GitHub passes through one described tool invocation, so the complete set of permitted actions is four signatures. Without that boundary, the question of what the agent may do to a repository is answered only by reading the entire codebase.

Establishes whether a technology was chosen or a fashion followed.
Q6Why a graph framework rather than a plain loop?

Explicit state and explicit routing. The lane determines the subsequent node by a pure function, so control flow is a graph that may be read. A prompt-chaining loop conceals routing within the model's output, which is precisely the part most requiring test.

Establishes framework literacy, and whether a trade-off can be articulated rather than a preference.
Q7Your tool server runs in the same process. Is the separation not illusory?

A fair objection, and the process boundary is indeed illusory; the code boundary is not. Under Docker the components are separate containers. On a single free service they were combined. The enforcement that matters, namely that the agent reaches GitHub only through described tools, is unchanged. Purchasing a second service to render a diagram accurate would be the wrong exchange.

Establishes whether a design is defended under pressure or abandoned. Concede the real point; retain the substantive one.
Q8How is indefinite re-running prevented?

By GitHub's own attempt counter. Only the first attempt is ever re-run. Because the counter belongs to GitHub rather than to process state, neither a restart nor a redeployment can reset it.

Establishes whether the superiority of stateless guards is understood.
Q9What occurs if the model returns nonsense?

Structured output is requested and validated. An unparseable or invalid response falls back to the informational lane, whose only action is to publish a comment. The failure mode is a less useful comment, never an unintended write.

Establishes whether the design anticipates the model being wrong.
Q10How would this scale to a thousand repositories?

Three things fail first, in order. The free instance, webhook processing being in-process background tasks, requiring a genuine queue. The diagnoses route, which employs a limit rather than pagination and silently truncates. The vector search, which is unindexed and requires an index, being one statement.

Establishes whether one's own bottlenecks can be identified. Three, in order, is materially better than a generality.

Security and access

Q11How do you authenticate to GitHub?

As a GitHub App. A credential is signed with the application's private key and exchanged for an installation access token limited to one installation and expiring within the hour, cached in memory for its lifetime. No personal access token exists anywhere in the system.

Establishes whether the implemented flow is genuinely understood.
Q12Why not a personal access token, which is simpler?

Such a token carries one person's entire access, does not expire until revoked, and cannot be scoped per repository. An installation token is scoped and self-expiring. When a credential was exposed, that distinction bounded the damage.

Establishes reasoning about blast radius rather than recitation.
Q13How is a webhook verified as genuine?

By a keyed hash computed over the raw request body using the shared secret and compared in constant time, so that the signature is not disclosed through timing. The check precedes parsing, since parsing attacker-controlled input before authenticating it is the defect.

Establishes whether the reasons for constant-time comparison and for ordering are known.
Q14Who may approve an installation?

Only the account that registered the application, determined from GitHub at the time of the request rather than from configuration liable to diverge from reality.

Establishes the authoritative-source habit a second time.
Q15Automatic approval of public repositories: is that not a vulnerability?

It is not, and the reasoning is the whole argument. A public repository's build logs are already readable by anyone. Reading one discloses nothing previously closed, so requiring approval would be permitting what is already permitted. Private logs are a genuine decision and a person still makes it. The rule is narrow, requiring both an explicitly selected repository list and every repository public.

Establishes whether one can reason about what a control protects, rather than adding controls reflexively.
Q16Why refuse an all-repositories installation if everything is public today?

Because approval is a statement about the future. Such an installation covers every repository the account subsequently creates, and the available evidence on whether the relevant event is delivered for those repositories is self-contradictory. The assertion therefore cannot be honoured and is refused rather than guessed.

Establishes whether ambiguous evidence is met by failing closed.
Q17A repository is made private after automatic approval. What then?

The corresponding event is delivered and approval withdrawn, but only where the source was automatic. An owner-approved installation is never withdrawn automatically, that being the application overruling a deliberate human decision.

Establishes whether the design extends beyond the expected path.
Q18It is made public again. Is approval restored?

Deliberately not. Were it restored, approval would be reversible by any party able to alter a repository's visibility, placing the gate in the hands of the applicant rather than the approver.

Establishes whether a privilege-escalation path can be identified in one's own design.
Q19Where is the user's token stored?

Nowhere. It is discarded at the conclusion of the sign-in exchange together with the refresh token. The session cookie holds the user identifier and login, signed.

Establishes session design, and awareness of what is being traded.
Q20The administrative endpoint has no request-forgery token. Why is that acceptable?

A fair challenge. The mitigation is that the route requires both a valid session and that the caller be the owner, and it was verified that an unauthenticated request with a well-formed body returns 401 with the row unchanged. It is not a substitute for protection upon a larger surface; with one write route and one authorised person it is a stated and bounded gap rather than an oversight.

Establishes the handling of a genuine weakness. Defending it as flawless is the wrong answer; stating the bound is the right one.
Q21The tool server is on a public URL. Is it exposed?

Reachable, not usable. The host header is compared against an allowlist and a mismatch returns 421. Traffic through the platform router carries the public hostname, which is not listed; the application's own loopback call carries a host that is. Tested in both directions.

Establishes awareness of rebinding attacks, which is a genuinely advanced answer.

Data, memory and evaluation

Q22Explain the memory feature.

Each log extract is embedded into 384 dimensions by a local model and stored in a vector column. Upon a new failure a cosine search locates the nearest previous diagnosis, and above the threshold it is supplied to the model as context. It is retrieval-augmented generation across the project's own history.

Establishes whether embeddings can be explained without vagueness.
Q23Where did the threshold come from?

Measurement. Distances were compared between known-related and known-unrelated pairs and the threshold set where they separated. Below it, unrelated failures matched and the supplied context degraded the diagnosis. The evaluation later identified a defect in the untested region near the boundary, which was corrected and documented.

Establishes — and this is the single question most worth preparing — whether a number was measured or felt. "It seemed right" fails.

Cost, latency and disclosure. It is free per call, introduces no network hop into the critical path, and does not transmit the log to a second third party. The weights are contained within the image so that a cold start does not download them.

By a 24-case reference set with known-correct lanes in four groups, including a deliberately ambiguous middle zone. Presently 91.7 per cent overall and 95.2 per cent upon unambiguous cases. It exercises the production classifier but never routes to action nodes, so execution publishes nothing.

Establishes whether evaluation occurs at all. Most comparable projects have none, and this answer is conspicuous.
Q26Why report two accuracy figures?

Because three of the cases are constructed to be arguable. Movement among them is noise; movement among the remainder is signal. A single blended figure would conceal the distinction rendering the metric useful.

Establishes literacy in metrics, which is a strong differentiator.
Q27Why Postgres with a vector extension rather than a vector database?

The vectors describe rows already residing in Postgres. A dedicated store would introduce a service, a synchronisation problem and a second failure mode, to solve what one ordered query already solves. Operation

Q28What happens if the server is asleep when a webhook arrives?

It is lost; GitHub does not retry. This was measured rather than assumed. The remedy is an external requester maintaining availability. The platform's own scheduler was attempted first and does not work: across seven hours a ten-minute schedule should have fired approximately forty-two times and fired none, silently.

Establishes knowledge of one's real failure modes. Admitting lost deliveries is far stronger than claiming unprovable reliability.
Q29How is it known to be working at present?

By a preflight script performing ten checks in approximately thirty seconds. It interrogates each dependency directly, verifies the gate state of every installation, confirms the deployed bundle, examines recent delivery outcomes, and asserts that the protected routes still refuse anonymous callers. Establishes operational maturity. Very few comparable projects possess this.
Q30What would you do next?

In order: a genuine job queue, so that processing survives a restart; pagination, before the row count renders the present limit dishonest; a scheduled visibility re-check, withdrawal presently depending upon deliveries that a sleeping server loses; and an index when the search becomes slow.

Each has a stated occasion. None is a rewrite.

Establishes prioritisation. Occasions rather than aspirations are the distinction.
